# Popup 打开与翻译期间响应性

## Problem Frame

用户在网页刚打开时点击扩展图标，偶尔看不到 Popup 或感觉完全无响应；页面已经发起翻译、存在大量“翻译中”节点时，同样可能无法及时打开或操作 Popup。

调查确认这不是单一的“启动时计算 DOM 数量”问题：未主动翻译前，内容脚本不会扫描页面。页面翻译开始后则确实存在同步全 DOM 扫描、文本可见性判断和批量 loading 回填；同时 Popup 把“翻译命令已被页面接受”与“首轮翻译任务完成”绑定在同一个消息响应上，导致按钮和消息链路等待过长。Popup 初始化还把后台配置读取作为所有主要控件的硬门禁，真实 action popup 的打开时序目前没有自动化门禁。

本次修复目标是让 Popup 和页面控制在页面加载、扫描及长时间翻译期间始终具有可观察反馈和可用的取消入口，而不是只缩短某个网络超时。

真实 action popup 调查使用当前 `dist` 和 `chrome.action.openPopup()` 完成：普通页面约 0.85-1.63 秒出现并可用；超大 DOM 仍在流式加载时，最慢约 1.47 秒发现 Popup target、2.34 秒到 DOMContentLoaded、2.70 秒内确认 React 主按钮可用；约 2388 个 loading 节点存在时约 1.0-1.25 秒可用。没有复现永久打不开，但秒级空窗足以被感知为首次点击无效。

用户进一步确认现场表现为：点击工具栏图标后 Popup 外框完全不出现，过一段时间才出现；不存在空白 Popup、控件禁用、按钮长期 busy 或一闪而过。由此可将问题定界为 Action Popup target 创建/调度延迟，而不是 Popup React 初始化或配置门禁。页面自身初载压力也可能触发该现象；扩展主动翻译后，同步扫描和 loading 回填会进一步制造目标页 renderer 长任务与整体 CPU 压力。

## Key Flows

- F1. 网页刚打开时打开 Popup
  - **Trigger:** 用户在网页仍在加载时点击扩展图标。
  - **Steps:** 浏览器创建 Popup；Popup 立即展示可见壳层；配置与页面状态异步加载；超过短暂等待阈值时显示“正在连接页面/加载设置”，而不是无反馈；成功后解锁操作，失败后提供重试和设置入口。
  - **Outcome:** 用户能确认点击已经生效，不需要反复点击或等待网页完全加载。
  - **Covered by:** R1, R2, R3, R4

- F2. 发起大页面翻译
  - **Trigger:** 用户点击翻译当前页面。
  - **Steps:** 页面接收命令后立即确认；Popup 不等待完整翻译；页面先上报准备/翻译状态，再分片扫描与插入 loading；进度持续更新；失败通过任务状态显示。
  - **Outcome:** Popup 很快恢复可操作，网页主线程可以处理滚动、恢复和新命令。
  - **Covered by:** R5, R6, R7, R8, R9

- F3. 翻译进行中重新打开 Popup
  - **Trigger:** 页面存在在途翻译，用户再次点击扩展图标。
  - **Steps:** Popup 创建后订阅一次页面进度并读取快照；显示当前翻译状态；恢复原文入口无需等待现有翻译请求完成即可使用。
  - **Outcome:** 翻译任务不能阻止 Popup 打开或让状态倒退。
  - **Covered by:** R1, R4, R5, R10, R11

## Requirements

**Popup 打开与初始化**

- R1. Popup 必须先渲染可见界面，再异步获取配置、快捷键和页面进度；任何单个初始化请求挂起都不得表现为点击图标完全无反馈。
- R2. 配置加载仍不得使用 fallback 覆盖真实设置；加载较慢时显示明确的局部加载状态，失败时提供原地重试和设置入口。
- R3. Popup 初始化只解析一次目标标签页，并只执行一次“订阅实时进度 + 读取初始快照”的流程，避免重复活动标签查询和重复进度请求。
- R4. 新的进度事件不得被较晚返回的旧快照覆盖；同一标签页导航到新文档后不得沿用旧文档的翻译状态。
- R4a. 本次首要性能目标是缩短用户点击工具栏图标到 Action Popup target 创建的延迟；Popup 内部配置重试属于次要韧性改进，不得替代主线程响应性治理。

**命令与任务生命周期**

- R5. `translate-page` 消息响应只表示命令已被内容脚本接受，不等待规则加载、DOM 扫描、loading 渲染、网络翻译或全部可见批次完成。
- R6. Popup 收到接受确认后立即解除本地 busy；后续 preparing/translating/complete/partial/error/idle 状态完全由页面进度通道驱动。
- R7. 命令异步执行后的规则、扫描、渲染、调度或后台错误必须进入可见终态，不能因立即确认而变成静默失败或未处理 Promise rejection。
- R8. 页面开始任务后尽早上报 translating 0/0 或等价准备状态，让 Popup 和 Badge 在扫描前获得反馈。
- R9. 内容脚本的页面任务仍由现有 generation/taskId 管理；新翻译或恢复必须让旧任务停止产生 DOM 副作用和迟到进度。

**主线程响应性**

- R10. 初始 DOM 候选收集和 loading 节点安装必须分片并定期让出宏任务，不能在一个同步任务中处理完整大页面。
- R11. 每次让出后检查任务代际；扫描或 loading 中收到恢复/新翻译时应尽快停止旧任务，并清理本代际产生的临时包装和 loading。
- R12. 分片不得改变正文识别、父子去重、TextNode 可逆包装、渲染器选择、可见优先和动态页面语义。
- R13. 动态页面大批新增/删除的进一步优化不作为本次首要范围，除非测量证明它是两个报告场景的直接主因。

**可验证性**

- R14. 增加真实 action popup 生命周期测试或等价浏览器级测量，至少记录点击/打开到 Popup 文档创建、首屏可见、配置可用的时间；普通扩展标签页打开 `popup.html` 不能作为唯一证据。
- R15. 增加大 DOM、慢翻译和翻译进行中打开 Popup 的性能/响应性门禁，覆盖 Popup 首屏、命令确认、首个进度和恢复响应。
- R16. 诊断和测试不得记录网页正文、API Key 或完整用户配置，只记录耗时、节点数、段落数、状态和任务标识。

## Acceptance Examples

- AE1. **Covers R1-R3.** Given 网页仍在加载且后台配置冷启动，when 用户点击扩展图标，then Popup 壳层在可接受时间内可见并展示加载状态；设置按钮可用，配置成功后控件解锁。
- AE2. **Covers R5-R8.** Given 页面包含大量可翻译节点，when 用户点击翻译，then Popup 在收到“已接受”后解除 busy，不等待所有 loading 或翻译结果；随后通过进度显示翻译中。
- AE3. **Covers R10-R12.** Given 1000 个简单段落或等价大 DOM，when 扫描和安装 loading，then 页面任务分片让出主线程，期间恢复命令能够被处理，旧任务不会继续插入 loading。
- AE4. **Covers R4, R10.** Given 页面正在翻译，when 用户重新打开 Popup，then Popup 显示最新进度，较旧快照不会覆盖实时事件，恢复入口可操作。
- AE5. **Covers R4.** Given 同一 tab 从已翻译页面导航到新页面，when 用户立即打开 Popup，then 新页面不显示上一文档的“显示原文”或旧进度。
- AE6. **Covers R7.** Given 命令已经确认但规则加载或扫描随后失败，when 任务收口，then Popup 收到 error 状态，页面不永久残留 translating/loading。

## Success Criteria

- 用户点击扩展图标后始终能快速看到 Popup 或明确加载反馈，不需要等待网页或翻译完成。
- Popup 的翻译按钮不再等待完整页面翻译 Promise。
- 大页面翻译期间网页可以处理恢复、滚动和后续命令，避免秒级同步长任务。
- 翻译状态在 Popup 关闭、重开和标签页导航后保持真实且不倒退。
- 测试能分别证明 Popup 创建、配置解锁、命令确认和页面任务执行四个阶段，而不是只验证最终翻译结果。

## Scope Boundaries

- 不通过缩短翻译服务超时掩盖 Popup/Content 协议问题。
- 不把 DOM 翻译任务迁移到 service worker；DOM 状态仍由 content script 管理。
- 不添加后台全局消息锁。
- 不允许 Popup 在配置未知时保存 fallback 偏好。
- 首期不引入完整的第二份配置缓存；先提供加载状态、超时提示和重试，只有实际测量证明配置读取是常见瓶颈时再评估脱敏快照。
- 不在本次重写扫描规则或改变可翻译内容范围。
- IndexedDB 永久挂起、后台孤儿请求、page-progress 存储竞争等可靠性问题单独跟踪；若性能测试证明它们直接阻塞 Popup，再纳入实施计划。

## Key Decisions

- 先修协议，再修时间切片：命令立即确认解决错误等待关系，分片解决页面主线程长任务，两者缺一不可。
- 进度通道是任务状态唯一来源：Popup 不从翻译命令 Promise 推断完成。
- Popup 初始化先做低风险去重：只解析一次标签页、只读取一次进度快照。
- 配置加载采用可见降级而非不安全 fallback：慢时提示，失败可重试，但不允许写入未知配置。
- 性能分片使用宏任务让步和时间预算，不能只用微任务或简单把一个长任务拆成两个长任务。
- 当前证据不支持把配置读取或大量 loading 节点本身视为 Popup 永久打不开的直接根因；优先修复可证明的命令等待关系和页面长任务，同时增加真实 action popup 性能门禁。
- 现场问题属于“外框延迟出现”：第一实施优先级改为切分扫描和 loading 长任务、减少连续 CPU 占用；命令立即 ACK 紧随其后，用于解除 Popup 操作与翻译任务的错误等待关系。

## Outstanding Questions

### Deferred to Planning

- Chrome action popup 的自动化应使用工具栏点击、`chrome.action.openPopup()` 还是单独的手工性能门禁？
- 分片扫描采用异步扫描函数、阶段式扫描还是 async generator，哪种最少改动且能保留父子去重？
- 标签页进度采用 documentId、导航事件清理还是内容脚本启动 idle 握手来隔离新文档？
- 命令 ACK 是否携带 generation/taskId，以便进度与当前任务严格对应？
- Popup 配置加载多长时间后显示“加载较慢”和重试最合适？
